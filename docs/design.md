## 术语

| 术语 | 含义 |
|---|---|
| 花园(Garden) | 一份存档:地点、时间来源、物种表、土壤格网、植物、历史 |
| 操作(Op) | 玩家的意图,如种植、浇水、换土;带花园内日期;是同步的基本单位 |
| 事件(Event) | 模拟产生的结果,如"兔子啃食""病害发生",带原因;不同步,随每日记录保存 |
| 每日记录(DayRecord) | 一个已提交日子的结果:植物状态、天气、操作、事件、模型版本;不可变 |
| 预测(Projection) | 从"现在"向未来推演的临时结果,不入存档 |
| 检查点(Checkpoint) | 完整状态快照,用于天气校正后的重新推演和新设备的快速恢复 |
| confirmed / provisional | 某一天使用的是观测天气 / 预报或估算。离线需要提交一天时只能取一条天气序列,用某个典型的历史情景,**不是气候平均** |
| 沙盒花园 | 时间来源为历史年份的花园 |

## 数据分层

| 层 | 内容 | 本地保存 | 同步 | 能否重算 |
|---|---|---|---|---|
| 输入 | 地点、场地分析结果、物种表(含自定义)、花园日历设置 | 是 | 是 | — |
| 玩家意图 | 操作日志 | 是 | 是(基本单位) | — |
| 外部事实 | 每日天气记录 | 是 | 以服务端为准 | 不能,来自外部 |
| 已提交历史 | 每日记录(含事件) | 是 | 是,不可变 | 仅天气校正时产生修订版 |
| 当前状态 | 植物、土壤格网、动物丰度、杂草种子库 | 是 | 待定(#106) | 可由检查点 + 其后的记录重建 |
| 检查点 | 完整状态快照 | 是 | 待定(#106) | 可重建 |
| 预测 | 未来推演与风险区间 | 否 | 否 | 随时重算 |

**关键判断(随里程碑一并确认)**:
- **空间化(#55)应在 M1 打底**,即使 M1 里互动很少。换土、局部浇水、遮荫、动物、杂草都建立在土壤格网之上,晚做意味着重写模拟和数据格式。
- **统一的 `step`(#102)要先于任何时间相关功能**,否则补算、预测、沙盒各写一套,"等价"无法保证。
- **AR 是核心卖点(见技术选型),但依赖真机验证**;建议 M1 并行做 #29 的最小原型,而不是等到最后。

## v1 内置方案(AI 移到 v2,#123)

**决策(2026-11-24)**:云端 AI 有联网和费用问题,AI 功能放到 v2 并走订阅模式(商业模式细节仍待定,#111)。v1 **完全内置、可离线**,用内置数据和端上小模型取得**相近**的效果,目标不是与大模型完全等同。

**原则**:能查数据的不用模型去猜;能确定性计算的不用模型;确实需要机器学习的,用端上小模型,结果交给玩家确认。

### 对照

| 功能 | v1 内置做法 | 与云端 AI 相比 |
|---|---|---|
| 土壤 pH 与肥力 | 内置 SoilGrids 子集查表 + 玩家校正(#118) | **更好**:实测数据优于从照片猜 |
| 日照与遮挡 | 天文计算 + 照片天空遮罩(#119、#109) | **持平或更好**:是几何,不是 AI |
| 土壤颜色、湿润、植被占比 | 现有像素启发式 + 小型分割模型 | 略弱,够用于玩法 |
| 识别照片中的植物 | 端上分类器,候选限定在目录内,玩家从前几名确认(#117) | **接近**,但仅限封闭的常见物种;真实准确度未验证 |
| 用文字找物种 | 多语言模糊搜索 + 性状筛选(#116) | 对名称持平;对自由描述**较弱** |
| 物种生长参数 | 内置性状数据,缺失按科属默认并标 estimated(#115) | 持平,且不会编造 |
| 外观 | 程序化生成,描述符来自目录性状和选色(#121) | 持平:这一层本来就不需要 AI |
| 植物抠图取色 | 端上分割(#119) | 接近 |
| URL 导入物种、自由描述解析、全景生成、LLM 精修 | **不做**,留到 v2 订阅(#123) | 无法内置 |

### 物种目录(封闭世界的"自定义物种",#115、#116)

- **玩家的"自定义物种"在 v1 是:从内置目录里选**(几千种常见植物),而不是现场解析任意输入。目录之外的植物在 v1 不支持,这是与 AI 方案最大的差别。
- **数据来源**(均为调研所得,许可需在 #122 中逐项核对):
  - FAO EcoCrop:2,568 个物种,含温度上下限、pH、降水、生育期天数,许可为 CC BY 4.0;FAO 已不提供单独下载,可通过 GAEZ 平台或 CGIAR 数据中心的 Parquet 副本取得。**局限**:偏重作物,观赏植物和乔木覆盖不足,多年生植物的生育期只记为 365 天,对我们的生命周期模型(#103)帮助有限。
  - GBIF 骨干分类(CC BY 4.0):学名、科属、同义名,用于搜索与科属默认值。
  - TRY、AusTraits(CC BY 4.0)等性状库:株高、叶型等,用于外观描述符。
- **合并策略**:以学名为键合并多个来源;每个字段记录来源与置信度(`sourced` / `estimated`,同「物种数据」);缺失字段用科属默认,并明显标注。
- **玩家可调整**:参数不满意可以手改,改动记录为玩家覆盖,不会被后续目录更新冲掉。
- 体积、更新方式(随游戏更新还是单独下载)待 #115 评估。

### 拍照识别(可选,#117)

调研到的候选(事实来自检索,未经我们在真实花园照片上验证):

- **Pl@ntNet-300K v2 模型**:六个变体,在其自身测试集上约 0.82–0.85;代码为 BSD-2,**权重受 DINOv3 许可门控**,再分发前要读清授权。
- **BioCLIP 2**:MIT 许可,ViT-L/14,覆盖约 95.2 万个分类单元,支持用物种名列表做零样本分类(可以直接把候选限定为我们的目录)。**未找到文件大小**;社区有 ONNX/TFLite 转换,质量未核实。
- **iNaturalist Seek**:离线可用,约 8 万物种,离线时只返回物种和图片;**权重是否开放未找到**。
- 小型端上分类器报告的体积在十几到几十 MB 量级(例如 17 MB、42 MB),但缺少可信的准确度数据。

做法:候选限定在目录内,并按位置做先验(这是我们的设想,尚未验证),玩家从前几名里确认,识别结果只当搜索辅助。**如果 #117 的实测达不到可用准确度,v1 就不带拍照识别,只保留搜索。**

### 场地分析的内置做法(#118、#119、#109)

- 土壤:SoilGrids 的 pH 与有机碳(六个深度)压成粗网格查表。当前版本许可为 CC BY 4.0,旧版本是带相同方式共享要求的 ODbL,**以实际使用的版本为准**;下载体积未找到,待实测。玩家可手动校正。
- 日照:天文日长 × 云量 × 场地遮挡,场地遮挡来自照片的天空遮罩。
- 端上推理:Unity Inference Engine(原 Sentis)可以运行 ONNX 模型,社区有 MobileSAM 和 U-Net 分割的示例。**注意**:Meta 文档称其目前不使用 NPU 硬件加速;有人报告新式 ONNX 导出会让输出失真,需要用旧的导出方式。速度必须在 iOS/Android 真机上实测。

### 外观与气候

- 外观:程序化生成不依赖 AI。可参考 EZ-Tree(MIT,Three.js,Weber–Penn 模型,50+ 参数)、SeedThree(MIT,早期 alpha)和一个 MIT 的 Unity L-system 项目(成熟度未核实);生产版在 Unity 里用 C# 移植算法并保留署名(#121)。
- 气候:预测集合(#104)和离线回退都需要气候数据。**WorldClim 限非商业使用**,不能直接内置到商业发行的游戏里,需要另选商用安全的来源(#120)。

### 取舍与风险

- **覆盖**:目录之外的物种、自由描述、任意网址都做不到;观赏植物和乔木的参数多数是 estimated,可靠度低于默认物种。
- **识别的真实准确度未知**:公开的数字来自精心整理的测试集,不等于玩家手机拍的花园照片。
- **体积与速度**:目录、土壤子集和模型都会增加安装包体积;端上模型在中低端手机上的速度未知。
- **许可与署名**:多项数据是 CC BY,需要署名页;模型权重的许可要逐个核对(#122)。
- **披露**:v1 没有云端 AI,但端上机器学习模型是否需要在 Steam 披露要核实(#25)。
- **本地化**:目录的多语言俗名覆盖不均,中文名可能需要另外整理(#113)。

## 架构(已退役原型的现状,仅作历史参考)

```
定位(GPS/手填) ─┐
照片(可选)      ─┼→ SiteAnalyzer ─→ SiteAnalysis(土壤/周边植被/全景)
                 └→ WeatherProvider ─→ WeatherDay[90]
                                   ↓
       初始布局(按适宜度自动生成) → simulate() → Snapshot[0..90]
                                   ↓
              Garden3D.sync(snapshot) ← 时间轴(播放/拖动)
```

玩家编辑布局只修改"今天"的植物列表,随后重新 `simulate()`;时间轴只是在快照数组上取值,因此预测与回放成本很低。(这是原型的做法;生产版的时间轴分为"已确认历史"和"预测",见「时间模型:现实日历 + 预测快进」。)

## 服务接口(`src/services`)

- `SiteAnalyzer.analyze(loc, photo?) → SiteAnalysis`。当前 `mockAnalyzer`:取照片下半部分 64×64 像素的亮度/绿色占比/红褐度,亮度越低土壤越湿,越红褐越黏重;无照片时由经纬度种子(mulberry32)确定性生成。
- `WeatherProvider.getDaily(loc, days) → WeatherDay[]`。当前 `mockWeather`:按纬度和季节计算气温,马尔可夫链生成降雨。前 `FORECAST_DAYS`(14)天标记为预报,其余为气候估算。
- 计划替换:v1 分析 → 内置土壤数据 + 端上分割(见「v1 内置方案」);v2 订阅 → 视觉大模型。天气 → Open-Meteo。

### 场地分析的可信度(目标,#109)

- **照片能推断的有限**:土壤颜色、湿润程度、周边植被可以大致看出来;**pH 和肥力无法从照片可靠测得**。目标做法是结合所在位置的土壤数据集(v1 内置 SoilGrids 子集,#118;v2 才可能引入其他来源),并明确标注"推断"。每项带置信度。
- **玩家可校正**:允许手动输入(如土壤检测结果)或调整,校正值覆盖推断值,并记录来源,避免后续"待精修"又把它改掉。
- **日照的缺口(已核对代码)**:`SoilAnalysis.sunHours` 只用于界面显示,模拟并不使用它;模拟只读天气里的 `sunHours`,而 mock 天气的日照与纬度、日长无关。目标:日照 = 天文日长(由纬度和日期算出)× 云量折减(来自天气)× 场地遮挡系数(来自照片、周边植被和建筑),三者分开;场地遮挡是场地分析的输出,随季节只在有叶/无叶时变化。

## 生长模型(`src/sim/growth.ts`)

每天对每株植物:

- 四个胁迫因子,取值 0..1:
  - 温度:日均温落在物种 `idealTemp` 内为 1,偏离 12°C 衰减到 0;最低温 <0°C 上限 0.3,最高温 >38°C 上限 0.4。
  - 水分:土壤湿度低于物种需求按 2.5 倍扣分;超出需求 0.35 以上按 2 倍扣分。
  - 光照:`日照小时/10/物种需光`,上限 1。
  - pH:落在物种范围内为 1,偏离 2 衰减到 0。
- 限制因子 = 四者最小值。
- 成熟度每日增量 = `1/growthDays × 限制因子 × (0.6 + 0.4×肥力)`。
- 健康度每日向限制因子靠拢:`health += (限制因子 − health) × 0.25`。
- 土壤湿度:`m += 雨量/25 − (0.04 + 0.003×max(0, tMax−15) + 0.0015×日照) − 0.0008×植物数`,限制在 0.05..1。所有植物共用一个土壤水分池。
- `simulate()` 是纯函数,返回 `Snapshot[]`(第 0 项为初始状态)。

## 与 Little Botany 的 GDD 模型对比

来源:Jamonnak & Cheng, 2017, *Little Botany*(教育类手机游戏),全文见 `docs/references/`(任务 #32 已核对)。

### 论文做法(已核对全文)

- 公式(论文式 2,针对番茄):`GDD = (Tmax + Tmin) / 2 − Tbase`,Tbase "通常为 50°F"(约 10°C)。论文**没有**给出下限截断、上限温度、成熟所需积温,也没有说明 GDD 如何驱动游戏中的成长。
- 阶段表(论文表 3)以**种植后天数**划分番茄的 10 个阶段(1–3 天、3–5 天……45–60 天),每阶段按"白天/夜间 × 晴/多云/雨雪雷"给出需水量(mm),下雨则为 0。也就是说阶段推进是按天数,不是按积温。
- 每株植物有种植时间戳,用来计算已生长天数;番茄在种植幼苗后约 60–85 天收获。
- 天气来自 Weather Underground 的 HTTP 接口(按机场站点取当日/历史逐时数据,取时间、温度、湿度、事件、天气状况五项),位置经 Google Maps 地理编码;玩家可选择历史年份(如 2012)。只有实时与历史,没有预报。
- 公测版只有番茄、胡萝卜、洋葱 3 种蔬菜,计划扩展到 20 种。土壤只是玩法背景,没有土壤分析或 pH。
- 玩法上是"每日维护":浇水、喷农药、收获;下雨当天不必浇水。
- 评估只做了可用性/可玩性问卷(为期三周),没有验证生长模型与真实生长的吻合度。"提升园艺知识""对真实园艺更感兴趣"两项得分相对较低。

### 标准 GDD(通用农学做法,非论文原文)

论文公式不含截断。常见的修正形式为 `GDD_日 = max(0, (min(Tmax, Tupper) + max(Tmin, Tbase)) / 2 − Tbase)`;植物累计 GDD 达到物种的成熟积温即成熟。成熟积温和 Tupper 需另找农学来源(任务 #33)。

### 与现有模型的差异

| 方面 | 现有模型 | GDD 模型 | 影响 |
|---|---|---|---|
| 温度的作用 | 理想区间内恒为 1,区间外线性衰减的"胁迫" | 温度越高发育越快,低于 Tbase 完全停止 | 现有模型中 15°C 与 28°C 的薰衣草速度相同;冬季种植的结果偏乐观,橡树在 5°C 日均温仍有约 0.67 倍速度 |
| 成熟时间 | 固定 `growthDays`,与季节无关 | 积温阈值,冷季自然变慢、暖季变快 | 同一植物在不同季节/纬度成熟天数不同,更符合现实,预测更有意义 |
| 发育阶段 | 单一 0..1 成熟度 | 论文按**天数**划分 10 个阶段并给出各阶段需水表(未与积温挂钩) | 现有模型无法表达开花期、结果期需水不同;阶段划分我们应按积温而非天数,否则季节无关的问题依旧存在 |
| 时间基准 | 以天为单位 | 种植时间戳 + 历史/实时天气 | 玩家可回放真实年份,也便于做回归测试 |
| 其他限制因子 | 水分、光照、pH、肥力 | 水分(按阶段与天气);无 pH、光照、肥力 | 这部分现有模型更完整,应保留 |
| 预报 | 前 14 天预报 + 气候估算 | 无,只有实时与历史 | 未来预测是我们独有的方向,论文不能提供参考 |
| 验证 | 无 | 仅问卷,无生长吻合度验证 | 两边都没有拿真实生长数据校验过,见任务 #40 |

结论:论文只给出了一个未截断的 GDD 公式和一张按天数的阶段水分表,**并没有提供可直接照搬的积温阈值**,GDD 参数必须另找来源。现有模型缺少"热时间"概念,这是最大的真实性缺口;需要保留的是水分/光照/pH/肥力的胁迫乘子,以及极端温度惩罚。论文中值得借鉴的是玩法:按阶段和天气决定当天要不要浇水(下雨免浇)。

### 提议的模型(待 #33、#34 实施,未改代码)

- 物种新增 `tBase`、`tUpper`、`gddToMaturity`;成熟度日增量改为
  `GDD_日 / gddToMaturity × min(水分, 光照, pH, 极端温度惩罚) × (0.6 + 0.4×肥力)`。
- 原来的 `idealTemp` 不再决定速度,只用于高温胁迫(超过上限的部分)和适宜度提示。
- 迁移时的占位推算:`gddToMaturity ≈ growthDays × (理想温度中点 − tBase)`。例如番茄理想温度 18–30°C,取 tBase = 10°C,得 60 × 14 = 840 GDD。这个数只是为了与旧行为大致对齐,**真实数值要在 #33 中按农业资料确定**。
- 阶段(#35):在成熟度区间上按积温划分 苗期/营养生长/开花/成熟 等阶段,每阶段有自己的水分与光照需求(论文表 3 的阶段和需水量可作为番茄的初始参考,但它按天数划分,需换算)。
- 每日维护(#39):参考论文,按阶段与当天天气计算"今天要不要浇水",下雨免浇;与 #14 的灌溉操作合并设计。
- 不确定性(#36、#104):14 天预报之外不能用气候平均(会抹平极端日),应用多个历史年份的真实天气序列做情景集合并给出区间,见「时间模型 → 预测的含义」。
- 生命周期(#103):以上"成熟积温"针对一季内的发育;一年生、多年生、木本的跨年行为见「生命周期与多年生长」。
- 历史年份回放(#37):选一个过去的年份推演,既是玩法,也能当作测试数据。

### 风险

- 不同物种的 Tbase 差异大,取错会让某物种在整个季节都"不生长";必须有数据来源。
- 积温模型把"过冷不生长"做实后,冬季的预测会出现大量停滞,界面需要解释原因(例如显示"低于基础温度")。
- 论文没有提供积温阈值,若找不到可靠来源(#33),某些物种(如樱花树、橡树)只能用估算值,需要在界面或文档中注明。

## 生命周期与多年生长(目标,#103)

**问题**:现模型里每种植物有一个 `growthDays`,到点"成熟"就结束。这对番茄、向日葵这类一季作物勉强成立,但橡树 120 天、樱花树 110 天"成熟"不符合现实(木本植物要多年);GDD 方案(上一节)同样隐含"一季作物"的假设。现实日历模式下游戏可以连续运行数年,必须能表达一年生、多年生和木本。

**物种增加生命周期字段**:

| 类型 | 例子(默认物种) | 行为 |
|---|---|---|
| 一年生 | 向日葵;番茄(在有霜的气候里按一年生栽培) | 一季内从发芽到成熟、采收/结籽,之后生命周期结束(正常结束,与"衰败死亡"区分);需要重新播种 |
| 多年生草本 | 薰衣草、草坪 | 冬季地上部分减少或休眠,春季重新发育;每年积温重新累计 |
| 灌木 | 玫瑰、绣球 | 多年存活,逐年增大,按物种有休眠与花期 |
| 乔木 | 橡树、樱花树 | 需要多年才达到成熟体量;落叶或常绿;年增长量受当年天气影响 |

(以上分类是通用植物学常识;各物种的具体年限、休眠条件需要可靠来源,与 #33 一起整理。)

**模型变化**:
- 把原来的单一"成熟度 0..1"拆成两层:**年内发育阶段**(0..1,休眠解除后重新开始累计积温,每年重置)和**多年体量**(木本和灌木逐年累积,决定尺寸)。
- 休眠由低于 Tbase 的持续低温和日长触发,休眠期不累计积温;解除休眠的条件按物种设定。
- 外观由体量决定大小,由年内阶段决定叶、花、果是否出现(与 #50 一致);落叶树冬季为光秃形态。
- 自定义物种需要的生命周期字段多数只能按科属推断,标记 estimated。

**对其他部分的影响**:
- 预测窗口:90 天看不到多年变化。窗口默认仍是 90 天,但可以延长到一年以上看季节循环;更长的"若干年后"预览成本高,是否支持取决于性能基准(#114)。
- 补算("离开几个月")必然跨季节,休眠与落叶要走同一个 `step`。
- 衰败(#63)与正常结束要在事件和报告里分开表述,避免把"一年生植物到季末结束"当成失败。

## 生态互动、本地动物与花园衰败

目标:花园不是一株株独立的植物,而是一个会互相影响的系统。选错搭配、放任不管、或者所在地的动物找上门,花园都可能变差;玩家要能在时间轴上提前看到风险,并有办法应对。

### 现状的缺口

`PlantInstance` 有位置(`x`、`z`),但 `growth.ts` 完全没用:所有植物看到同样的光照,共用一个水池,互相没有影响;植物不会死;没有动物。要做互动,模拟必须"空间化"。

### 植物之间的互动

| 互动 | 机制 | 备注 |
|---|---|---|
| 遮荫 | 高大植物按冠幅和高度遮挡邻近植物,光照因子下降;太阳方位随纬度和季节变化(北半球遮荫在北侧) | 喜阴物种(如绣球)可从中受益 |
| 水分与养分竞争 | 土壤按格网记录水分和养分,植物按根系半径吸收;密植时互相抢 | 取代单一共享水池 |
| 拥挤 | 冠幅或根系重叠超过阈值,双方生长都受抑制 | |
| 土壤反馈 | 重养分消耗型植物压低肥力;豆科固氮抬高肥力;落叶影响肥力与 pH | 幅度要小,避免一两株就改变整个花园 |
| 化感作用 | 个别物种抑制邻近植物 | 只收录有可靠依据的少数物种 |
| 搭配关系 | 物种间"有益/有害/中性"关系表 | 每条带**证据等级**;只有证据较强的才产生数值效果,民间搭配说法仅作提示 |
| 病虫害传播 | 同科植物聚集时病虫害更容易扩散;单一种植风险高 | 依赖物种的科属信息 |
| 扩散与杂草 | 部分物种会自播或蔓延占地;裸土和无人照看的区域会长杂草 | 杂草作为通用竞争者 |

### 本地动物

- **按位置决定会来哪些动物**:根据经纬度和栖息地类型得到可能出现的动物群落(如鹿、兔、松鼠、鸟类、蜗牛/蛞蝓、蚜虫、毛虫、蜜蜂、蝴蝶、蜂鸟、蚯蚓)。数据来源待调研(#60),需核实其使用条款;离线时用内置的粗粒度地区表,联网后可精修(同「离线降级」)。
- **角色**:
  - 传粉者:提高开花结实,依赖蜜源花卉。
  - 食草动物(鹿、兔、松鼠):啃食嫩叶和果实,不同物种的"可口程度"不同。
  - 害虫(蚜虫、毛虫、蜗牛):造成叶片损伤并传播病害。
  - 天敌与鸟类:压制害虫;需要栖息地。
  - 土壤动物(蚯蚓):改良土壤。
- **种群模型**:每类动物保留一个每日丰度状态,受季节/气温、花园提供的食物与庇护所、玩家的干预影响;种群大于阈值时造成损害。保持简单,不模拟个体。
- **玩家手段**:围栏、防鸟网、鸟巢、水体、杀虫剂等(#62)。要有取舍,例如杀虫剂同时伤害传粉者和天敌,不是万能解。

### 花园会变差,但要可预期、可恢复

- 失败形式:叶片受损、落叶、病害、植物死亡、杂草占地、某个物种霸占花园。死亡是新增机制(现在只有健康度下降),且要有"濒死"阶段,让玩家来得及补救。
- 连锁反应:植物死亡留下空位,杂草或扩散物种趁机进入;害虫增加又伤害更多植物。
- **可恢复**:清理、补种、防护之后花园能恢复,不做不可逆的"一次清盘"。
- **解释性**:每个损害都要记录原因(如"兔子啃食""被橡树遮荫""与邻株争水"),在时间轴和事件日志中展示(#65),避免玩家觉得是随机惩罚。
- **难度**:提供休闲模式(损害更轻、恢复更快)和标准模式(#66)。这是 cozy 类游戏的重要卖点,不能做成生存压力。

### 模拟结构变化

- 空间化:状态增加植物位置、土壤格网、动物丰度等;每日顺序与接口见「模拟接口」。
- 邻居查询用空间哈希,植物数量在数百以内时开销可控;需要在 C# 模拟程序集里实测(#114)。
- **随机性**:动物到访、病害等是概率事件。随机数由 `花园 id + 日期 + 种子` 确定,所以同一设备、同一版本下推演结果可复现;跨平台和跨语言的边界见「确定性的边界」(#64、#105)。
- **预测不确定性**:预测不再是单一结果,而是集合(天气情景 × 事件种子),给出"大概率发生/可能发生"的风险区间,方案见「时间模型 → 预测」。计算量需要实测(#114)。
- 编辑布局后仍然整体重新推演,保持现有流程。

### 对其他模块的影响

- **物种数据**:新增 `ecology` 块:冠幅、根系半径、耐阴性、是否固氮、是否重养分、化感作用、科属、对各类害虫的易感度、对各类食草动物的可口程度、对传粉者的蜜源价值、提供的栖息地、扩散性、**原产/入侵状态(按地区,#112)**,逐字段带来源与置信度。入侵状态用于:种植建议不推荐入侵物种,并区分"本地原生"对动物的价值。自定义物种的这些字段大多只能按科属推断,标记为 estimated,宁可保守(不产生强效果)。
- **渲染**:动物出现、啃食痕迹、枯萎、杂草(#67)。
- **同步**:动物与杂草是由确定性模拟得出的,不单独同步,只同步玩家操作。
- **Steam/AI 披露**:v1 的动物数据用内置的地区表,不依赖 AI,保证离线可玩;若 v2 引入服务端或 AI 解析,按「发布注意」处理。

### 风险

- 数值平衡:互动越多越容易出现"看不懂为什么死"或"怎么都死",需要大量调参和测试(#66)。
- 证据质量:搭配相生相克有大量民间说法,不能当作事实写进数值。
- 数据可得性:按位置得到动物群落、物种对动物的"可口程度"没有现成的统一数据,多数会是估算,界面要标注。
- 计算量:空间化、多种子推演会明显增加计算,移动端要特别关注。

## 模拟接口(目标,#102)

生长、生态、操作、时间模型各自都要求改 `simulate()`,散落在各节里。统一为一个**单日推进函数**,其他一切都是它的循环:

```
step(state, dayInput, species, rules) → { state', record }

state     = { plants[], soilGrid, weedSeedBank, animalAbundance, ... }
dayInput  = { date, weather, ops[], seed }      // ops = 当天已安排的操作(含周期规则展开)
species   = 物种表(默认 + 自定义)
rules     = 难度/模式、模型版本
record    = DayRecord(植物状态、天气、操作、事件及原因、modelVersion)
```

- 单日内的固定顺序:当日操作 → 天气 → 土壤格网(水/养分)→ 光照遮挡 → 植物生长与竞争 → 动物种群 → 损害与死亡 → 杂草/扩散。
- **所有时间相关功能都是 `step` 的循环**:实时逐日 = 每天调用一次;离线补算 = 连续调用 N 次并写入每日记录;预测 = 从当前状态用情景天气连续调用(不写记录);沙盒快进 = 连续调用并写入记录。因此"补算与一直开着等价"是**结构上**成立的,而不是靠测试碰巧一致。
- `step` 必须是纯函数:不读系统时钟、不读全局变量、随机数只来自 `seed`(由 `花园 id + 日期 + 种子` 派生)。
- 已退役原型的 `simulate()` 相当于"只含生长一步、没有操作、没有随机"的 `step` 循环;C# 实现从 `step` 的规格(#102)直接写起,不移植原型代码。

### 确定性的边界

此前几处写了"各设备推演出同样的结果",这样说过头了,修订如下(原型退役后只剩一种语言,"跨语言对拍"不再存在,只需考虑跨平台):

- **同一设备、同一版本**:逐位可复现。
- **跨平台(ARM/x86)**:浮点结果可能有微小差异。连续量用容差比较;但**离散事件**(丰度超过阈值就触发啃食、随机数落在概率区间内)可能因为微小差异而翻转,混沌放大后整个历史会不同。
- 对策(#105):PRNG 按规范固定为整数算法;触发判定用的关键量(种群丰度、阈值)整数化或定点化;测试时连续量和离散事件分开测,离散事件用注入的随机序列测。同一份测试向量在 x86(开发机、CI)和 ARM(手机、Mac)上都要通过。
- **更重要的是不依赖"各设备重算得出一样的结果"**:已提交的日子不可变并同步(见「回放」),其他设备采用记录,不重算;重算只发生在本机,例如天气校正或预测。

### 性能预算(#114)

文中多处出现"数百株 × 90 天 × 多个情景/种子"的计算量,目前都是估计。需要先定目标设备档位(如中端手机、Steam Deck),再在 C# 模拟程序集里实测空间化推演和集合预测的耗时(要在目标设备上测,不能只看开发机);在实测之前,关于"可以实时重新预测""补算一年可行"的说法都是假设。

## 时间模型:现实日历 + 预测快进(已确认)

花园在创建时选择时间来源:**现实日历**(默认,含快进预测)或**历史年份**(沙盒,见本节「历史年份选项」)。现实日历下,两种时间方式并存:

- **现实模式**:游戏的"现在"跟随真实日历,花园每天按**真实天气**推进。玩家逐日看到变化,浇水、除草等操作发生在真实的日期上。
- **快进预测**:玩家把时间轴拖到未来或让它快速播放,看模型推演的结果。**快进只是预览,不会提交**:已发生的状态只能随真实日历前进,所以玩家不能靠快进"跳过"真实时间。

### 已确认与预测的分离

```
 过去 ── 已确认(confirmed) ──┤现在├── 预测(projected,不入存档状态) ──→
        观测天气 + 玩家操作          预报 14 天 + 情景集合 + 计划中的操作
```

- 存档里的**花园状态**只到"现在"。未来部分每次由 `simulate()` 从"现在"推演得到,编辑布局或计划后重新推演(与现有流程一致)。
- 过去的每一天是 confirmed 或 provisional:confirmed 用的是实际观测天气;provisional 用的是预报或气候估算(例如离线时),联网拿到观测后校正。
- "天"的边界按**花园所在地时区**计算,而不是设备时区(桌面版手填位置时尤其要注意)。

### 预测的含义

- 预测由模拟模型给出,可靠度随距离下降。
- **用情景集合,而不是气候平均(#104)**:前 14 天用预报;之后不再用"平均天气",而是取多个历史年份**同一日期段的真实天气序列**(例如过去 10–30 年,数据来源见 #88)作为情景,每个情景各推演一次。理由:模型对极端天气是非线性的(最低温 <0°C 上限 0.3、最高温 >38°C 上限 0.4),平均值会抹平霜冻和热浪,使预测系统性偏乐观,区间也不诚实。
- **输出**:每天的中位数与区间(如 10%–90%),以及各类风险事件的发生概率。情景(天气)× 种子(动物、病害等随机事件,#64)共同构成集合;集合规模取小值并先对关键指标计算,具体数字待实测(#114)。
- 第 8–14 天的预报本身也不确定,可以随距离逐步过渡到情景集合,而不是在第 14 天硬切换(细节待 #104)。
- 沙盒(历史年份)花园的预测同理,但情景**排除该年**,避免偷看(#90)。
- 目前"AI"用于场地分析和物种解析(#11、#43),不负责预测;是否用大模型解释预测结果另议。

### 天气数据

- confirmed 的日子需要观测数据。观测/再分析数据可能有延迟,最近几天可能要用预报接口的过去数据补,具体来源与条款在 #10、#31 核实。
- 每个花园每天的天气记录以服务端为准(沿用"天气不参与冲突合并"),多设备使用同一份记录,避免各设备因取到的天气不同而产生分歧。
- 天气请求经服务端按网格点和日期缓存共享,客户端不直连第三方(#107):降低成本、统一商用授权(#31),也方便对位置做粗化(见「隐私与数据」)。
- 现实日历模式需要联网才能得到 confirmed 天气。完全离线(包括部分 Steam 玩家)时日子保持 provisional,用情景估算推进;这是可接受的降级,但界面要说明。

### 离开与补算

- 游戏没运行的这段时间,下次启动会把**所有真实发生的变化**补上,效果等同于"一直开着游戏":打开时按顺序补算缺失的每一天,每天用同一个推演步骤(见下「补算包含什么」)。随机事件(动物、病害)由种子决定,结果可复现。完成后展示"离开期间发生了什么"的报告(与事件日志 #65 一致)。
- **离开保护**:休闲模式下,离开期间的损害设上限,避免玩家回来发现花园全毁;标准模式不设上限,但有周期规则或防护的会受益。可选提醒(手机本地通知/推送,需玩家授权;Steam 版只有应用内提示)。
- **离线补算**:没有网络时无法取得观测天气,按气候估算补算并标记 provisional;联网后用观测天气替换,并**从最近的 confirmed 点重新推演**。因为 `step` 是纯函数、随机事件由种子决定、操作按日期记录,在**本机**重新推演是可行的(跨设备不依赖重算,见「确定性的边界」);但重新推演可能改变已经看到的结果,界面要提示"结果因真实天气修正而变化"(与 #21 一致)。

### 补算包含什么

补算与"一直开着"必须**等价**:同样的存档、同样的天气记录,不管是实时逐日走过去还是离开后一次补算,结果一致。不允许为了省时间做粗粒度近似(否则不同设备会得出不同结果,也破坏测试向量 #68)。每个缺失的日子都执行:

| 类别 | 内容 |
|---|---|
| 日历 | 日期推进、季节变化、由纬度和日期决定的日长与日照;植物的季节性(落叶、休眠、一年生植物结束生命周期等) |
| 天气 | 当天的观测天气,包括极端天气(霜冻、热浪、暴雨)对土壤和植物的影响 |
| 玩家安排 | 当天的计划操作和周期规则(滴灌、定期除草等)、防护措施的生效与失效 |
| 生态 | 动物种群的季节变化、病虫害发生与扩散、杂草生长与扩散、植物之间的竞争 |
| 事件 | 随机事件(种子决定)。节日类日历事件对植物、天气、动物没有机制性影响,只是装饰或内容,已确认不进 v1,后续作为纯内容任务再做,且不得影响模拟结果(#96) |

- **补算期间玩家无法响应**:有些损害本来需要玩家当天处理(如病害需要剪枝),离开期间只有已有的周期规则和防护能起作用,这正是「离开保护」存在的原因。
- **长时间离开**:数月甚至一年的补算是几百次空间化推演,要分块在后台线程执行并显示进度(#93)。需要在 C# 模拟程序集里实测耗时(#114);若太慢,优化实现而不是降低精度。
- **离开报告**:不逐日罗列,按重要度聚合(死亡、重大损害、丰收、极端天气),可展开看原因链(#94)。
- **设备时钟**:"现在"来自设备时钟,可能被改动。时钟回拨:忽略,取已见过的最大日期。时钟被调快:联网后与服务端日期核对,超出真实日期的天数是 provisional(没有观测天气,只能用气候估算),会被回滚。完全离线的单机玩法(如 Steam)无法校验,这是单人游戏,接受这一点(#95)。
- **沙盒(历史年份)花园**不补算:时间只在玩家推进时前进。

### 历史年份选项(沙盒)

玩家创建花园时可以不选现实日历,而是选**一个已经过去的年份**(如 2012)和起始日。花园在这一年的真实天气下运行,时间由玩家控制:可以暂停、逐日、倍速,**快进即提交**,不像现实模式那样只是预览。

| 方面 | 现实日历 | 历史年份 |
|---|---|---|
| "现在" | 真实日期 | 花园内的游标,由玩家推进 |
| 天气 | 观测 + 14 天预报 + 情景集合 | 该年当地的观测天气,全部已知 |
| 快进 | 仅预览,不提交 | 提交,可暂停/倍速 |
| 离开补算与保护 | 有 | 无;不玩时时间不走 |
| 回退 | 不可回退 | 可回到检查点重来 |
| 联网 | 需要观测天气,离线用估算 | 创建时一次取回整年天气,之后完全离线 |

- **创建后不可切换**:同一个花园里混用两种时间会让历史不一致。想玩两种,就建两个花园。
- **年份限制**:只能选已经结束的年份,可选范围取决于天气数据源的覆盖(#88、#31)。
- **预测不能偷看**:历史模式下"未来"的天气其实是已知的,但预测默认**不使用该年真实的未来天气**,而是用其他年份的真实天气做情景集合(同「预测的含义」),否则预测变成作弊。可提供"上帝视角"开关,显示该年实际会发生什么,适合学习和对照模型(#90)。
- **日历字段**:花园带 `calendar: {mode: real | historical, year, startDate, cursor}`。操作日志里的日期是花园内的日历日,不是设备的墙上时间。天气记录整年存入花园,多设备一致。
- **用途**:除了玩法,它还给我们提供固定的"地点 + 年份"天气夹具,用于回归测试(#38、#91)和模型校准(#40)。
- **时间轴标记**:可以从天气数据里算出热浪、霜冻、暴雨等极端日并标在时间轴上(只用数据本身,不引用外部事件资料)。
- **待决定**:沙盒花园是否计入成就、是否参与 Steam Cloud 与同步(#92)。倾向于成就中涉及"真实时间"的(如连续存活 N 天)不计沙盒。

### 回放(含往回拖查看历史)

时间轴往回拖可以查看已发生的状态(类似 Little Botany 的回看),数据来自每日记录。玩家还可以选一段时间范围,把期间发生的变化重新播放一遍,看清到底发生了什么(例如离开一周后,或者一株植物出问题之前的那几天)。回放是只读的:不改变花园状态,与"预测"(向未来推演)不同,它重现的是**已经发生的事**。

**能看到什么**:天气逐日变化、植物的生长与健康、土壤水分、玩家的操作被执行、动物出现、病虫害与损害、死亡与杂草,以及每个事件的原因(与事件日志 #65 一致)。

**控制**:播放/暂停、倍速、逐日、跳到上一个/下一个事件;可过滤(只看某一株、某类事件、只看我的操作);镜头可以自动跟随当前事件的位置。

**入口**:
- 时间轴上拖选一段范围,点"回放"。
- 离开报告中的"回放这段时间"(#94)。
- 事件日志中某条记录的"回放前后",自动选取事件前后的几天,并可对比事件前后的状态(#100)。

**数据:读记录,不靠重新推演**
- 每个已提交的日子写一条**每日记录**:各植物的成熟度和健康度(量化后存)、当天天气、被执行的操作、发生的事件及原因,以及**模型版本号**(#98)。体量很小(数百株 × 一年,量级为几百 KB),可以放心长期保存。
- 回放直接读记录。原因:游戏规则和模型会随版本更新,如果用新版本重新推演旧日子,会得出与当时"实际发生"不同的结果,回放就不再是历史了。
- 重新推演只在**天气校正**时发生(provisional → confirmed),此时产生该日的新修订版,回放显示最终修订版,可标注"已按真实天气校正"。
- 离开期间补算出来的日子同样写入每日记录,所以离开报告里的"回放这段"自然可用。
- 沙盒(历史年份)花园同样支持回放,回退重来后被放弃的时间线不保留。

**同步**:已提交的日子是**不可变**的:一旦某个设备提交并上传,其他设备不重新计算该日,而是采用已有记录("先确认者胜"),避免两台设备因版本不同得出不同历史。天气校正产生的修订版以服务端为准(#99)。

**渲染**:回放复用时间轴使用的场景同步(逐日状态喂给 `Garden3D`),动物、啃食痕迹、枯萎的表现依赖 #67;事件发生时的镜头聚焦和高亮是新增内容。

**后续可能**:把回放导出为延时视频,方便分享。当前不做、不排期。

### 注意与风险

- 现实模式下番茄要真等 60 天,节奏慢。快进只给预览,可能让一部分玩家觉得"不能玩快"。历史年份沙盒是对此的回应:想快速玩就创建历史花园。
- 离开期间的设计要谨慎:太严厉会让人不敢离开,太宽松又没有养护压力,需要通过休闲/标准模式和周期规则调节(#66、#86)。
- 对现有代码的影响:`Snapshot[]` 目前表示"今天起的 90 天预测",今后需要区分"已确认历史"和"预测";时间轴 UI 随之改动(#81、#85)。

## 园艺操作

玩家像真实园丁一样照料花园:浇水、除草、修剪、换土等,"不限于"这几种,所以要做成**数据驱动的操作系统**,新增一种操作主要是加数据和效果,不是改架构。

### 操作目录(首批)

| 类别 | 操作 | 效果与取舍 |
|---|---|---|
| 水 | 浇水(手浇/喷淋/滴灌)、周期规则 | 补充土壤水分;过量会积水、烂根;滴灌/规则可设"雨后跳过" |
| 杂草 | 除草 | 清除区域内杂草;早除成本低,长大后更费力;杂草会从种子库再生 |
| 覆盖 | 铺覆盖物(mulch) | 减少蒸发、抑制杂草,随时间分解并微量增加肥力 |
| 修剪 | 修剪、摘残花、割草、清理病枝、疏果 | 控制株型与冠幅(减少遮荫、改善通风而降低病害);摘残花可延长部分物种的花期;**时机因物种而异**,剪错季节会损失花或果 |
| 采收 | 采摘果实/蔬菜 | 产出与阶段有关;晚采会被动物吃掉或腐烂 |
| 土壤 | 换土 | 把区域内的土壤整体替换为指定类型(土质、pH、肥力、湿度);会扰动区域内的植物,需先移走或承担损伤;同时清空大部分杂草种子库 |
| 土壤 | 改良 | 堆肥/肥料提高肥力(过量烧根)、石灰升 pH、硫磺降 pH(都是缓慢生效)、松土改善排水 |
| 植物 | 移栽、疏苗 | 移栽有"休克"期;拥挤时间苗可减轻竞争 |
| 防护 | 防霜布、遮阳网,及 #62 的围栏、防鸟网 | 根据天气预报提前安排,在极端天气前保护植物 |

### 时间模型:操作带日期

现有流程只修改"今天"然后重新推演。园艺操作有时间性("第 5 天浇水"),所以:

- 每个操作是带日期的事件 `{day, type, target, params}`,目标可以是某株植物、一块区域或整个花园。
- 日期不晚于真实日历"现在"的视为已执行(入已确认历史);晚于"现在"的是**计划**,玩家可以修改或撤销,预测会按计划推演,时间轴上能看到效果。快进预览时不能把未来的操作"提交",只能随真实日历到来而执行(见「时间模型」)。
- 周期规则(如"每 3 天浇水,下雨则跳过")是一种计划,展开后得到一系列事件。
- 操作进入操作日志(扩展 #18 的 `place|remove|clear`),同步与回放都基于日志。
- 游戏的"现在"跟随真实日历(混合模式,已确认),见「时间模型」。

### 模拟中的位置

每日顺序见「模拟接口」:当日操作排在最前面,先于天气和生长。

- 水、养分、杂草种子库、土质都按土壤格网记录(依赖 #55),所以换土、局部浇水才有意义。现在的单一 `SoilAnalysis` 只作为格网的初始值。
- 操作的效果是对状态的确定性修改,不引入随机,随机仍只来自动物和病害事件。

### 物种数据

- 物种增加 `care` 块:适宜的修剪时机与耐受程度、是否可摘残花、采收阶段与产出、对过量浇水/施肥的敏感度。
- 自定义物种的 `care` 大多由科属推断,标记 estimated;缺失时用保守的通用修剪规则,不产生"剪错就损失"这种强惩罚。

### 同步与冲突

- 操作分两类:**累加类**(浇水、施肥、除草)多次都生效,按日志顺序全部应用,不丢;**设置类**(换土、改良目标)是覆盖状态,同一区域冲突时最后写入者胜。区域类操作的冲突规则比逐植物 LWW 复杂,单列任务 #78。

### 界面

- 工具栏选工具(水壶、锄头、剪刀、铲子、堆肥),点击单株或在地面刷涂区域;在时间轴选定的日期上安排;可撤销。
- 操作前预览效果(如显示受影响的格子),操作后显示发生了什么,并与事件日志一致(#65、#80)。
- 桌面(Steam Deck 手柄)、手机(触屏刷涂、AR)的操作方式要分别设计(#77)。

### 成本(已确认)

- **v1 不设经济系统**:没有货币,操作也没有精力或次数限制(#79)。难度差异靠生态压力和离开保护体现。Little Botany 的"卖果实换钱买种子"这类循环暂不采用,后续版本再评估。
- 因为操作免费,界面和规则要防止"无脑重复":例如过量浇水、过量施肥本身有惩罚,而不是靠成本约束。

### 风险

- 操作多了之后界面容易繁琐,需要合并(如一键"巡园")和默认规则,否则玩家每天点几十次。
- 修剪时机、土壤改良速度等真实园艺知识要有可靠来源,避免把错误做法写成规则。
- 换土、区域类操作依赖空间化模拟(#55),在此之前原型只能做单株的浇水和铲除。

## 物种:默认物种与自定义物种

### 两类物种

- **默认物种**:游戏自带 8 种(薰衣草、向日葵、玫瑰、绣球、番茄、草坪、橡树、樱花树),参数由我们维护(`origin: 'default'`),玩家不能修改或覆盖。
- **自定义物种**:玩家可以自己添加(`origin: 'custom'`)。**v1(完全内置)**:从内置物种目录里搜索或拍照识别后选择,不依赖云端,见「v1 内置方案」。**v2(订阅 AI)**:输入可以是 **图片、文字描述、URL** 三种之一,由服务端解析;URL 只接受官方或经过验证的物种来源站点。下面的「添加流程」「可信来源」是 v2 的设计。
- 两类物种使用同一套 `Species` 结构和同一个生长模型,模拟代码不区分来源。

### 物种数据

- 物种表以 JSON 为单一来源(见「技术选型再评估」),存档里携带玩家的自定义物种。自定义物种 id 带命名空间(如 `custom:<uuid>`),不会与默认物种冲突。
- 在原有字段之外增加:`origin`、`source`(来源 URL 或"图片/描述推断")、逐字段的 `confidence`(`sourced` 来自可信来源 / `estimated` 推断或按同类默认)、GDD 参数(`tBase`、`tUpper`、`gddToMaturity`,见上一节)。
- **设计要求**:已退役原型的 `speciesById` 读取全局常量 `SPECIES`,无法容纳自定义物种。C# 实现里物种表必须是模拟的输入参数(即「模拟接口」中 `step` 的 `species`),这也让 #28 的测试夹具能自带物种参数。

### 添加流程(v2:AI 解析,订阅)

```
图片 / 描述 / URL ─→ 服务端
   1. 识别物种(学名):图片和描述只用来识别,结果给玩家确认
   2. 取参数:以可信来源的数据为准,不由大模型凭空编造
   3. 缺失字段:按同科/同类型默认补全,标记为 estimated
   4. 返回草稿 ─→ 玩家确认/调整 ─→ 保存为 Species(origin: custom)
```

- **图片**:视觉模型给出候选物种(附置信度),玩家选一个;不确定时要求玩家补充描述。
- **描述**:文本解析出名称、习性;同样先落到具体物种再取参数。
- **URL**:先校验域名在白名单内,再由服务端抓取并解析;客户端不直接抓取。
- 参数的**来源与置信度要展示给玩家**,estimated 字段要明确标注,避免玩家误以为是权威数据。

### 可信来源(v2)

- 白名单由服务端维护,可更新,不写死在客户端。具体收录哪些站点(例如植物学数据库、政府/大学农业推广机构、官方植物志)及其使用条款、是否有可调用的接口,由任务 #42 核实后决定;在此之前不承诺任何具体站点。
- 抓取安全:仅 https、禁止指向内网/本机地址(防 SSRF)、限制响应大小与超时、不跟随跳转到白名单之外。
- 页面和用户描述的内容**一律当数据,不当指令**,防止通过网页或描述向大模型注入提示。

### 参数校验(v1 与 v2 都需要)

- 所有数值都必须落在合理区间内(温度、pH、需水、需光、生长天数、积温),越界即拒绝或截断并标注。
- `tBase < tUpper`、理想温度区间与 Tbase 的关系等做一致性检查。
- 无法确定物种或关键参数全是 estimated 时,允许保存,但在调色板里提示"参数不可靠"。

### 离线与同步

- **v1**:从目录选择,完全离线,不需要排队;选定的物种(含玩家调整的参数)随存档本地保存。
- **v2**:解析依赖服务端和大模型,**离线时不能解析**;离线时可以保存"待解析"草稿,联网后处理(同「离线降级」的排队机制)。
- 已确认保存的自定义物种随存档本地保存,之后完全离线可用。
- 同步沿用操作日志,新增 `addSpecies` / `removeSpecies` 操作;删除物种时,花园里已种的该物种植物需要处理(提示并一并移除,或保留只读)。

### 渲染:尽量还原真实物种

目标:自定义物种也要"看起来像那种植物",而不是套用同一个通用模型换个颜色。现状的问题:`garden3d.ts` 的 `buildPlant` 只按 `kind` 用几个基础几何体拼装,并且对 `sakura` 做了硬编码特判,无法扩展到任意物种。

**外观描述符 `appearance`**:每个物种(默认和自定义)都带一份结构化的外观描述,渲染只读它,不看物种 id。包含:

- 株型:直立 / 丛生 / 匍匐 / 攀援 / 莲座 / 簇生草丛 / 柱状 / 圆冠 / 垂枝 等,以及株高、冠幅。
- 叶:形状(针形、线形、卵形、裂叶、复叶、掌状等)、大小、排列(互生/对生/轮生/基生)、颜色、常绿或落叶。
- 花:有无、花瓣数、形状、大小、颜色、花序(单生/穗状/伞形/圆锥/头状)、花期所处的生长阶段。
- 果:形状、颜色、所处阶段。
- 树皮/茎的颜色,分枝密度与角度,季相变化(秋色、落叶、冬态)。
- 每个字段带来源与置信度(与参数一致)。**v1**:描述符由目录性状(株高、叶型、生长型)、科属模板和玩家选色生成,照片只提供颜色(端上抠图取色,#119、#121);**v2**:由服务端从物种资料、玩家描述和照片中抽取,大模型只做"把资料转成这个结构",不凭空补外观。

**分层渲染,逐层降级**:

| 层 | 内容 | 用于 |
|---|---|---|
| A 手工资产 | 精心制作的模型 | 8 个默认物种(逐步从基础几何体升级) |
| B 参数化生成 | 按描述符生成枝干骨架,再用实例化的叶片和花序填充 | 自定义物种的主要路径 |
| C 照片增强 | 玩家照片抠图,取叶/花的主色与纹理,可选十字面片叠加 | 玩家提供了植物照片时,叠加在 B 之上 |
| D 兜底 | 现有按 `kind` 的基础几何体 | 描述符不足或株型不在支持范围内,并提示"外观为近似" |

- **确定性**:同一描述符 + 同一种子,必须生成同一外观。存档与同步只保存描述符和种子,不保存网格,跨设备外观一致。
- **随生长变化**:成熟度缩放整株,并按生长阶段让器官依次出现(先叶、再花、后果);健康度和季节影响颜色。这样玩家能在时间轴上看到"真实植物"的生长过程。
- **株型覆盖**:v1 覆盖草本、灌木、乔木(圆冠/柱状/垂枝)、草丛、蔬菜类和基础花序。仙人掌、蕨类、棕榈、藤本等需要专门的株型,不在 v1;遇到时走 D 层并提示。
- **确认界面**:玩家保存前能看到外观预览,与参考图并排,可以调整株型、花色等,不满意再改(任务 #52)。
- **图片来源**:来源站点的图片是否可以直接当贴图,取决于其使用条款(#42);默认只从中提取颜色和形状信息,玩家自己的照片仅本地使用。
- **性能**:大量植物需要实例化和 LOD,风动用 shader 实现;植物数量按设备设预算(#53)。
- **AI 图像转 3D**:是否用它直接生成整株模型,质量、成本、授权和 AI 披露都未知,仅做调研(#54),不纳入当前方案。
- **与引擎的关系**:描述符是与语言无关的 JSON;生成器直接在 Unity 里用 C# 实现(不再经过 Web 原型)。外观不要求逐像素一致,所以不进入 #28 的数值测试夹具。

**风险**:描述符的准确度取决于资料质量;生成器能覆盖的株型有限,"像"的程度会因物种而异,不能承诺所有植物都高度还原。

### 风险

- 参数质量:来源站点对"成熟所需积温"这类数据往往没有现成数字,大量字段会是 estimated,可靠度低于默认物种。
- 版权与条款:图片和抓取内容的使用权、站点的抓取许可需要核实(#42)。
- 成本与滥用:每次解析消耗大模型额度,需要配额和限速(#47)。
- Steam 版:自定义物种依赖联网解析,属于 AI 内容,需纳入商店披露(#25);完全离线可玩的保障不受影响,因为默认物种始终可用。

## 渲染(`src/scene/garden3d.ts`)

- 天空:程序化渐变天空球;有照片时将照片贴在天空球内侧作为背景(目前是简单球面映射,非真正全景拼接)。
- 地面:颜色取自土壤分析,并随湿度变深。
- 植物:原型按 `kind`(flower/shrub/tree/veg/grass)由基础几何体程序化构建,按成熟度缩放,健康度低时向枯黄色插值;代码里对 `sakura` 有硬编码特判。后续改为由 `appearance` 描述符驱动,见「物种:默认物种与自定义物种 → 渲染」。
- 交互:OrbitControls;位移 ≤4px 的 pointerup 视为点击(区分拖拽);点击植物优先于点击地面。

## 已知限制

- 分析与天气是 mock,结果不反映真实环境。
- 照片不是真正的全景,视觉上会拉伸。
- 水分为单一共享池,没有按位置区分;没有浇水、除草、修剪、换土等园艺操作(见「园艺操作」,任务 #69–#80)。
- 植物之间没有互动(遮荫、竞争、病虫害),没有动物;位置字段未参与模拟(见「生态互动、本地动物与花园衰败」,任务 #55–#68)。
- 植物不会死亡,只有健康度下降。
- 没有积温概念:成熟速度与季节无关,冷季预测偏乐观(见「与 Little Botany 的 GDD 模型对比」,任务 #34)。
- 没有生命周期:植物到 `growthDays` 就"成熟"并一直保持,橡树 120 天成熟不符合现实,也没有休眠、落叶、一年生结束(见「生命周期与多年生长」,任务 #103)。
- 场地日照不参与模拟:`SoilAnalysis.sunHours` 只用于显示,模拟用的是 mock 天气的 `sunHours`,与纬度和日长无关(见「场地分析的可信度」,任务 #109)。
- 预测在预报期之外只有 mock 的气候估算,没有极端天气,因此偏乐观(见「预测的含义」,任务 #104)。
- 以上限制描述的是已退役的 Web 原型。该原型从未安装依赖、通过类型检查或运行(#6–#8 已作废),不再修复;各项限制由 C# 生产实现按对应任务解决。

## 离线优先与同步

目标:玩家在无网络时也能完整游玩(编辑布局、播放时间轴、预测),联网后自动与云端同步,并用真实数据校正预测。

### 本地优先

- 所有状态保存在本地(浏览器用 IndexedDB,桌面版用文件)。存档带 `schemaVersion`,启动时迁移。
- 本地存档内容:场地分析结果、物种表(含自定义)、天气记录与缓存(带获取时间)、花园当前状态、检查点、操作日志、每日记录、待处理任务队列。分层与同步范围见「数据分层」。
- 生长模拟本来就是纯函数且完全在本地运行,因此离线可用。

### 操作日志

- 所有玩家意图都是操作:`{opId, deviceId, lamport, day, type, target, params}`。`day` 是花园日历日(现实日历下是真实日期,沙盒下是游标日期)。类型包括 `place|remove|clear`、园艺操作(`water|weed|prune|amend|replaceSoil|…`,见「园艺操作」)、`addSpecies|removeSpecies`、周期规则的创建与取消。
- **修订**:原先写的"当前花园 = 初始状态 + 按序重放操作日志"不再成立,因为状态还取决于逐日模拟。现在是:当前状态 = 最近检查点 + 其后的操作与已提交记录(见「数据分层」)。操作日志仍是同步的传输单位。
- 删除用墓碑记录,避免已删植物被另一设备复活。

### 离线降级

| 能力 | 离线行为 | 联网后 |
|---|---|---|
| 天气 | 用最近一次缓存;超出缓存范围用气候估算,界面标注"估算" | 拉取真实预报,重新推演,提示预测变化 |
| 场地分析 | 本地启发式(照片像素统计,即现有 mock),标记"待精修" | v1:无需联网,内置方案的结果即最终结果;v2(订阅):排队调用视觉大模型,结果替换并提示 |
| 定位 | 手填或沿用上次位置 | - |
| 编辑与预测 | 完全可用 | - |
| 现实日历下的逐日提交 | 无观测天气:按情景估算推进,日子保持 provisional | 用观测天气校正,从最近确认点重新推演(#83) |
| 自定义物种解析(v2) | 保存"待解析"草稿 | 排队处理 |

### 同步与冲突

- 同步为上传本设备未确认的操作、下载其他设备的操作;服务器按 `(lamport, deviceId)` 排序。
- 冲突规则:以植物为粒度,最后写入者胜(LWW);删除优先于同一时刻的修改。
- 场地分析和天气不参与冲突合并,以服务端较新的版本为准(例外:玩家手动校正的场地值不被"精修"覆盖,见「场地分析的可信度」)。
- **迟到操作**(修订,#106):离线设备产生的操作,日期可能早于服务端已提交的边界,而已提交的日子不可变。规则:不改写历史,操作在**最早未提交的日子**生效并标记"延迟生效";若目标已不存在(植物已死亡或被移除)则丢弃并通知玩家。
- **提交者**:同一花园的每个日子只由一方提交,**先上传该日记录者胜**,其他设备采用该记录。离线期间本地提交的日子是 provisional;联网后若服务端已有该日,本地记录被丢弃,本地操作作为迟到操作重放。
- **Steam Cloud 是文件级同步**:冲突时由 Steam 让玩家选一个版本,没有应用层合并。v1 的 Steam 版按"单设备或轮流使用(PC / Steam Deck)"设计,冲突时提示选择较新的存档。它与自建云同步是两套冲突语义,需要分别测试(#106)。
- 同一个花园能否在多台设备上同时游玩未明确;按上面的规则可以容忍,但体验上以"一个主设备 + 其他设备查看/少量操作"为目标。
- API key(视觉模型等)只放在服务端,客户端经代理调用,不打包进客户端。

## 服务端(目标,#107)

多个功能都依赖服务端,但此前只在各处零散提到。集中列出职责:

| 职责 | 说明 |
|---|---|
| 账号与同步 | 操作日志、每日记录的同步与"先上传者胜"仲裁(见「同步与冲突」) |
| 天气代理与缓存 | 按网格点 + 日期缓存共享;客户端不直连第三方;统一商用授权(#31) |
| AI 代理(v2) | 物种解析、场地分析精修、全景生成;API key 只在服务端;配额、限速、内容审核(#47)。v1 没有这一项,照片抠图与场地分析都在本机完成 |
| 物种来源抓取 | 域名白名单、SSRF 防护、解析(#42、#43) |
| 区域数据 | 动物群落、土壤数据集、原产/入侵状态(#60、#109、#112) |

- **账号**:Steam 版可用 Steam 身份;手机端用什么登录方式未定(#107)。**不登录也要能完整单机游玩**,账号只用于同步和 AI 功能。
- **降级**:服务端不可用时,客户端按「离线降级」运行。
- **成本**:天气可以按网格共享缓存,成本摊得很薄;AI 调用是按次计费且难以共享(每个玩家的照片不同),成本会随用户增长。**商业模式没有定**(#111):若 Steam 是一次性买断,但 AI 功能持续消耗服务端费用,就需要免费额度、按次或订阅等配额策略;这影响 #47 的设计,需要用户决定。

## 隐私与数据(目标,#108)

花园天然带有敏感数据(家庭住址附近的位置、住宅照片),此前设计里没有涉及:

- **位置**:精确 GPS 属于敏感数据。天气、动物、土壤只需要约 0.1° 量级(十公里左右)的精度,上传服务端时**取整到网格点**;精确坐标(用于日照和 AR)只保存在本机,或加密后同步。
- **照片**:v1 的照片只在本机处理(端上分割、取色、识别),**不上传**,这大幅降低隐私风险;以下规则针对 v2 的订阅 AI 功能。照片可能带人脸、门牌、车牌和 EXIF 里的 GPS。上传前去掉 EXIF,可在本机先缩小;发给第三方视觉模型之前必须**告知并取得同意**;服务端默认**不保留原图**,除非玩家选择同步;玩家可以删除。
- **自定义物种**的图片和描述同样处理,并做内容审核(#47)。
- **删除与导出**:玩家可以删除账号与云端数据;删除要覆盖服务端缓存和备份。
- **合规**:不同地区的法规(例如欧盟 GDPR、美国各州隐私法)和目标人群(是否面向儿童;Little Botany 是教育游戏,我们的定位尚未明确)会带来额外要求,需要法务确认,本文不断言具体条款。
- **披露**:Steam 的 AI 内容披露(#25)与隐私声明一起准备。

## Steam 发布

### 方案

- 客户端:采用 Unity 桌面构建,通过 Steamworks.NET 接入 Steamworks(原 Electron/Tauri 方案已作废)。
- 存档:本地文件存档交给 Steam Cloud 同步,与自建账号云同步是两条独立通道。默认只启用 Steam Cloud,避免双重同步冲突;自建云同步作为移动端 / 跨平台的补充。
- 功能:成就(如首次开花、花园全部成熟、连续存活 N 天)、Steam Deck 手柄操作与界面缩放、可选 Steam 云存档。

### 桌面端与移动端的差异

- 桌面没有 GPS 和 AR:位置手填或导入,照片从文件导入。
- 移动端(手机浏览器 / App)负责 GPS、拍照和 AR 模式。后续可以让手机把位置和照片发送到桌面存档。
- AR 模式在 Steam 版中不可用,需要在商店页说明。

### 发布注意

- Steam 要求披露使用 AI 生成内容的情况。v1 没有云端 AI,但端上机器学习模型(拍照识别、分割)是否需要披露,发布前按 Steam 当时的规定核实(#25);v2 的订阅 AI 功能(物种解析、全景生成等)必须披露。
- 调用外部 API 的游戏需要服务端代理和费用控制;完全离线可玩是 Steam 版的基本保障。
- 签名、自动更新和 Steam 构建上传流程待任务 #22–#25 展开后补充。

## AR 模式(目标,尚未设计,#110)

AR 被认为是核心卖点,但目前设计里只有一句话,且 README 里还写着"WebXR"(已随 Unity 决策过时)。需要设计的问题:

- **坐标系**:花园单位约 1 米,锚定在检测到的地面平面上。GPS 和指南针只能做粗略对齐(手机精度有限),**不承诺厘米级对齐真实地块**。
- **持久锚点**:下次打开能否把花园放回同一块真实位置,取决于平台能力(ARKit / ARCore 各自的持久化能力不同,是否需要云锚点或视觉定位服务)。尚未调研,不作承诺。
- **渲染**:AR 模式下不渲染程序化天空、地面和全景背景,只渲染植物、动物等;需要遮挡和光照估计才能自然;自定义物种的性能预算(#53)在手机上更紧。
- **与时间轴、回放的关系**:AR 里同样可以拖动时间轴、回放;预测的风险高亮要在 AR 视角下可读。
- **桌面没有 AR**:桌面版用普通 3D 视角,AR 相关功能要在商店页说明。
- 先做 #29 的最小真机原型再决定投入。

## 本地化与单位(#113)

- 界面语言:目前文档和界面是中文;是否做英文及其他语言要尽早定,因为物种名、事件原因文案(#65)、AI 返回的说明都要本地化。
- 物种以**学名**为跨语言的稳定标识,显示名按语言映射。
- 单位:°C/°F、mm/in、米/英尺;日期格式。模型内部统一用公制,只在界面转换。

## 技术选型再评估

背景:需求从"浏览器里的 MVP"扩展为:手机上的 GPS + 相机 AR 体验、离线优先与同步、Steam 上架。原选型(Web + Three.js)按这些需求重新评估如下。

### 对需求的逐项评估

| 需求 | Web + Three.js | Unity(C#) |
|---|---|---|
| 手机 AR | **短板**:WebXR 仅 Android Chrome 支持,iOS Safari 不支持。iPhone 用户无法使用核心玩法 | AR Foundation 统一 ARKit/ARCore,iOS 和 Android 都支持 |
| GPS + 相机取景 | 可用,但相机与 AR 管线受浏览器限制 | 原生支持 |
| 离线优先 | PWA + IndexedDB,可行 | 本地文件/SQLite,更直接 |
| Steam 上架 | 需 Electron/Tauri 封装,可行,Steam Deck 上体验一般 | Steamworks.NET 成熟,Windows/Mac/Linux/Steam Deck 同一代码库 |
| 3D 表现(大量植物、风吹、季节) | 手写渲染与资源管线,工作量大 | 实例化渲染、Shader Graph、地形与植被工具齐全 |
| 应用商店分发 | PWA 在 iOS 受限,需再封装 | 原生打包 |
| 迭代速度 | 最快,无需安装 | 较慢,需 Unity 工程与真机调试 |

结论:Web 栈的最大问题是 iOS 没有 AR,而 AR 是游戏的核心卖点;再叠加 Steam 和移动端两条分发线,Web 栈需要维护 Web、Electron、移动封装三套壳。

### 其他候选

- **Godot**:对 Steam 友好,但 ARKit/ARCore 支持依赖社区插件,成熟度不足,不作为首选。
- **Unreal**:AR 与桌面都能做,但对本项目体量过重。
- **Flutter / React Native + 3D 插件**:3D 与 AR 能力依赖插件,Steam 不适用。

### 决策(已确认,任务 #27)

- **生产客户端:Unity(C#)**(用户已确认采用),一份代码覆盖 iOS、Android、Windows/Mac/Linux 及 Steam Deck。AR 仅在手机端启用,桌面端用普通 3D 视角。
- **Web 原型退役**(2026-11-24 评审后确认,#130,取代此前"保留原型"的决定):
  - 原因:原型从未跑通,也无法产出目标设备的性能数字;保留 TS 模拟意味着同一逻辑写两遍,并要为此维护测试向量对拍和移植任务;在线 demo 可由 Unity WebGL 导出代替;3D 与 UI 部分对 M0 要验证的模拟问题没有帮助。
  - 做法:模拟核心直接用 C# 写成**不引用 Unity 的纯程序集**(noEngineReferences),用 `dotnet test` 在 Unity 之外运行,迭代速度与 TS 相当;Unity 工程直接引用该程序集。M0 的统一 `step`、积温、生命周期、空间化最小版和性能基准都在这里做。
  - 前提:开发机的 .NET SDK 与 NuGet 可用(#131 确认);否则退回"保留无界面的 TS 模拟"方案,需另行决定。
  - 代码处理:`src/`、`package.json` 等原型文件**暂不删除**(#130 只改文档);待 C# 模拟程序集可用后再决定删除或归档。
- **服务端**:独立后端,v1 负责同步与天气缓存;v2 再增加 AI 分析与全景生成的代理(API key 不进客户端)。语言不限,建议与团队熟悉度一致。
- **本地存储**:SQLite 或 JSON 文件 + 操作日志,与「离线优先与同步」一节一致。

### 迁移风险与对策

- **模拟逻辑只有一份实现(C#)**:原型退役后不再有 TS 与 C# 两份实现,因此不需要跨语言对拍和移植任务。仍保留 JSON 测试夹具(物种参数、天气序列、期望快照)作为回归测试,在 x86 与 ARM 上都要通过(任务 #28);数值比较使用容差,离散事件的测法与跨平台边界见「模拟接口 → 确定性的边界」(#105)。
- **物种数据**以 JSON 为唯一来源,两端共同读取。
- **Unity 授权与体积**:发布前需核对授权条款是否适用于项目收入规模。
- **AR 在真机才能验证**:先做最小原型(#29)再决定投入。

### 与数据源相关的发现

- Open-Meteo 的免费接口限非商业用途。Steam 是商业发布,需要购买其商用方案或换用其他天气源(任务 #31,发布前核实条款)。
- 全景生成与视觉分析依赖服务端,离线时只能使用本地启发式降级,见「离线降级」。

## 开发环境与跨平台(#133)

问题:项目能否在 Linux、macOS 上开发,而不是只能在 Windows。以下是对现有仓库和技术栈的评审,**平台支持细节是设计时的认识,尚未实测**,由 #134 核实后更新本节。

### 现状

- 仓库里没有 Windows 专有内容:没有 `.ps1`、`.bat`、盘符路径或 Windows API 依赖。已退役的 Web 原型(Vite + TypeScript)本身跨平台。
- 缺少跨平台卫生配置(#135):没有 `.gitattributes`,Windows 上 `core.autocrlf=true` 会让文本文件在检出时变 CRLF,对 JSON 测试夹具、Unity 序列化文件和 shell 脚本都有风险;`.gitignore` 只有 Web 原型的条目,没有 Unity、.NET、macOS 的条目。

### 候选:xtool(在 Linux/Windows 上构建 iOS,#134)

[xtool](https://github.com/xtool-org/xtool)(MIT)自称"跨平台的 Xcode 替代品"。以下来自其 README 与 DocC 文档(2026-11-24 读取),**未实测**:

- **能做的**:在 Linux、WSL、macOS 上把 **SwiftPM 包**构建成 iOS 应用、签名、安装到真机(`xtool devices/install/launch`)。
- **要求**:需要从 Apple 下载 Xcode.xip(要登录 Apple ID),由 xtool 提取出 iOS SDK;登录开发者服务有 API Key(需付费的 Apple Developer Program)和密码(任意 Apple ID,但用私有接口,文档建议用一次性账号)两种方式。
- **文档没有说明的**:能否构建 Unity 导出的 Xcode 工程、Objective-C/C++ 是否支持、App Store 分发。README 只提到 2.0 beta 增加"building Xcode projects"和"compiling macOS apps",没有细节。

**评估(推断,待 #134 验证)**:
- xtool 的主要目标是 SwiftPM 项目,而 Unity 的 iOS 产物是一个 Xcode 工程(含 IL2CPP 生成的 C++ 源码、UnityFramework、Objective-C 与原生插件),这类工程是否能被它构建,文档没有保证。
- 即使 xtool 能构建 Xcode 工程,**Unity 生成这个 Xcode 工程的步骤**(iOS Build Support)按我的认识只在 macOS 版 Editor 上提供,需要核实。若属实,Linux 上仍然产不出 iOS 工程,xtool 只能接手"构建与签名"那一段。
- 可能的折中:Mac 只负责导出 Xcode 工程(可以是很少用的一台机器),Linux CI 用 xtool 构建签名。这需要 xtool 真能构建该工程,是实验性路线。
- **许可风险**:Xcode 的许可协议是否允许在非 Apple 硬件上使用其 SDK,需要核实并由法务确认;商业发行不能忽略。
- **稳定性**:2.0 是 beta;密码登录用私有接口,可能随 Apple 变动而失效,不适合作为发布流水线的唯一依赖。
- 结论:**xtool 可以降低对 Mac 的依赖,但目前不能当作"Linux 上完整构建 Unity iOS"的已验证方案**;在 #134 实测前,仍按"至少一台 Mac 或 macOS 运行器"规划。

### 已知需要核实的限制(#134)

- 用 IL2CPP 脚本后端打各目标平台的包时,是否必须在对应系统的主机上构建(尤其是 Windows 包需要 Windows 与 C++ 工具链、macOS 包需要 macOS);Mono 后端通常限制少。这会决定 CI 矩阵(#136)。
- Unity 的 Linux Editor 与 AR Foundation、Inference Engine 等包的兼容情况。
- 大小写敏感:Linux 文件系统区分大小写而 Windows 默认不区分,资源路径或夹具文件名大小写写错,在 Windows 上不报错、在 Linux/CI 上报错。约定:路径大小写严格一致,CI 在 Linux 上跑。

### 约定(待确认后写入 AGENTS.md)

- 构建、测试、夹具生成的入口用 `dotnet` CLI 和 Unity 命令行,不只提供 PowerShell 或批处理脚本;必须有脚本时提供 shell 与 PowerShell 两个版本,或用 `dotnet` 工具代替。
- 文本文件统一 LF(`.gitattributes`),JSON 夹具不得被换行转换改写。
- 路径用 `/`,代码里用 `Path.Combine` 之类的 API,不手拼分隔符。
- 同一份回归夹具要在 x86(Linux/Windows)和 ARM(Apple Silicon)上都通过(#28、#105、#136)。
